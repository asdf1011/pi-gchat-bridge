# Google Chat API issues NOT in the issue tracker

Two API limitations we hit while building the bridge (pi-gchat-bridge) that
have **no filed issue** in Google Issue Tracker (component 350158, Google Chat
API) as of Aug 14, 2026. Verified live against the API (service-account /
app auth, `chat.bot` scope). Ready to paste into
https://issuetracker.google.com/components/350158 when we want to file them.

---

## Issue 1: NOTIFICATION_TYPE_SILENT returns 403 for threaded messages

**Title:** Chat API: NOTIFICATION_TYPE_SILENT returns 403 when creating a message in a thread

**Component:** 350158 (Google Chat API)

**Summary:**
Sending a message silently (no push notification) via
`createMessageNotificationOptions.notificationType=NOTIFICATION_TYPE_SILENT`
works for top-level messages but returns **403 Forbidden** when the message is
created inside an existing thread (i.e. when `messageReplyOption` is present).
There is currently no way to create a silent message in an existing thread,
which forces bots to notify for intermediate messages (e.g. a streaming
placeholder) in threaded conversations.

**Repro (app auth / service account):**

```
POST https://chat.googleapis.com/v1/spaces/SPACE/messages?messageReplyOption=REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD&createMessageNotificationOptions.notificationType=NOTIFICATION_TYPE_SILENT
Body: {"text":"test","thread":{"name":"spaces/SPACE/threads/THREAD"}}
```

Response: `403` (silent unsupported with `messageReplyOption`).

**Control tests (all verified Aug 14, 2026):**

| Variation | Result |
|---|---|
| + silent + messageReplyOption (above) | 403 |
| thread in body, NO messageReplyOption | 200, but `thread` is **ignored** — message lands in a NEW thread |
| messageReplyOption, NO silent | 200, correct thread, but notifies |
| `PATCH ...?updateMask=thread` to move a message into a thread | 400 "Unsupported path name in message field mask" — thread placement is not patchable |

**Expected:** `NOTIFICATION_TYPE_SILENT` honored for threaded messages, or an
alternative way to create a message in a thread without notifying.

**Related:** #292235340 (app-auth capabilities). (An earlier draft also cited
#316196511, which turns out to be "Disable Notifications for Instruction
Changes" — unrelated.)

## Issue 2: PATCHing message text drops MARKUP_SYNTAX_MARKDOWN — RESOLVED

**Status: fixed / workable as of Oct 17, 2026.** The Oct 16, 2026 release notes
announce per-request `markupSyntax` on create *and update*. Verified live: the
field is honoured when sent in the **body** of a text PATCH
(`PATCH ?updateMask=text`, body `{"text": …, "markupSyntax":
"MARKUP_SYNTAX_MARKDOWN"}`) — the response echoes MARKUP_SYNTAX_MARKDOWN and
`formattedText` keeps the Markdown source.

What still does NOT work (unchanged, still worth reporting):

| Variation | Result |
|---|---|
| `updateMask=text,markupSyntax` | 400 "Unsupported path name in message field mask" |
| `updateMask=markupSyntax` (body only markupSyntax) | 400, same |
| `updateMask=*` | 200, response says MARKDOWN, but the message is legacy |
| `updateMask=text`, no markupSyntax in body | 200, resets to MARKUP_SYNTAX_CHAT |

So Markdown on update requires the undocumented combination above; the field
still isn't a maskable path. Keep the section below as the original report (it
is the clearest repro for "make markupSyntax patchable").

Implemented in pi-gchat-bridge: `ChatClient.updateMessage()` sends the field in
the body (commit f7e87f9).

**Original report**

**Title:** Chat API: PATCHing message text resets MARKUP_SYNTAX_MARKDOWN to legacy Chat formatting

**Component:** 350158 (Google Chat API)

**Summary:**
`markupSyntax: MARKUP_SYNTAX_MARKDOWN` (GA Aug 7, 2026) renders standard
Markdown in created messages. But any subsequent `PATCH` of the message's
`text` resets the message to legacy Chat syntax (`*bold*`, `_italic_`, …), and
`markupSyntax` is not a valid `updateMask` path. This makes it impossible to
stream/update a message's text incrementally and keep Markdown rendering —
bots that stream long replies must delete the placeholder and post a fresh
message when done, leaving a "Message deleted" stub in the conversation.

**Repro (app auth / service account):**

1. `POST /v1/spaces/SPACE/messages`
   Body: `{"text":"**bold**","markupSyntax":"MARKUP_SYNTAX_MARKDOWN"}`
   → renders as bold. ✓
2. `PATCH /v1/{messageName}?updateMask=text`
   Body: `{"text":"**bold** more"}`
   → message now renders `**bold** more` as **literal asterisks** (legacy
   syntax) — Markdown styling lost.
3. `PATCH /v1/{messageName}?updateMask=markupSyntax`
   → `400` (not a valid `updateMask` path).

**Expected:** Either `markupSyntax` should be patchable (so streaming updates
keep Markdown), or `PATCH text` should preserve the message's original
`markupSyntax`.

**Use case:** Streaming/agent bots (e.g. the Chat bridge to a coding agent)
patch a placeholder as text streams in, then replace it with a fresh Markdown
message — the patch-reset is the only reason the replace is necessary.

**Related:** #157909720 (standard Markdown in Chat), #377230196 (Markdown +
links in one message), #428659965 (Markdown tables).

## Issue 3: no way to notify users when an existing message is updated

**Title:** Chat API: message updates can't notify recipients — bots must post a new message to ping "reply ready"

**Component:** 350158 (Google Chat API)

**Summary:**
Notifications are only produced by `spaces.messages.create` (via
`createMessageNotificationOptions`, incl. NOTIFICATION_TYPE_SILENT to suppress
them). `spaces.messages.patch` / `update` accept only `updateMask` and
`allowMissing` — there is no notification parameter at all, and a PATCH never
notifies. `allowMissing: true` even creates a message, and per the docs the mask
is ignored, but the request still offers no notification control.

Consequence for streaming bots (agent/coding bridges): to watch a reply stream
in, the bot patches a placeholder — usually created silently to avoid ping
noise. When the answer is ready there is no way to notify, so the bot must post
the completed text as a *new* message and delete the placeholder. That leaves a
"Message deleted" stub in the thread and doubles the message count per reply.
The only alternative is to keep the placeholder and never notify, which is
worse (the user has to sit in the chat and wait).

**Ask:** an update-time notification control — e.g.
`updateMessageNotificationOptions.notificationType` on PATCH (FORCED /
NOTIFICATION_TYPE_SILENT / default), so a bot can stream silently into a
placeholder and notify once when it finishes. Failing that, `allowMissing` +
client-assigned IDs would be a usable workaround only if the create-through-
PATCH path could notify (`allowMissing` currently can't create a notifying
message in a thread either, since silent 403s with `messageReplyOption` see
Issue 1).

**Workaround used by pi-gchat-bridge:** create the answer as a new message (the
ping), then delete the placeholder; if that create fails, keep the placeholder
and patch the answer into it (no ping, but no lost reply). Configurable with
`BRIDGE_REPLACE_ON_FINISH`.

**Related:** Issue 1 above (silent + threads), #166140696 (typing indicators —
same family of "let a bot show progress without spamming"), #428659965 (tables).

**Not the same thing:** editing a message in the Chat client also sends no
notification (Google Chat Community thread 374000881) — that's user-facing
behaviour, not this API gap.
